# MediaFlow 智能体架构：调研结论与改造方案

> 2026-10 调研。目标：让管家「小媒」不仅能按关键词找选题，还能**搜博主、看对标账号作品、拆解爆款**，并把结论沉淀下来用于写稿。

## 1. 参考资料与要点

| 来源 | 关键结论 | 对我们的意义 |
| --- | --- | --- |
| Anthropic《Building effective agents》 | 能用固定流程就别用自主 agent；agent 用在步骤不确定的任务上 | 写稿流水线保持代码编排 ✅（已做到） |
| Anthropic《Writing effective tools for agents》 | 工具少而精、按工作流合并；按「服务/资源」命名空间；只返回高信号字段，用可读名字代替 ID；分页/截断要有默认值并提示下一步；报错要告诉模型怎么改 | 平台能力做成**少量通用工具 + platform 参数**，不要 7 平台 × N 功能 |

## 2. 现状评估

**合格的部分**

- 写稿是固定流水线（选题 → 写 → 硬检查 + AI 评审 → 重写 ≤3 → 存草稿 → 后台配图），三个入口共用。
- 管家是单 agent + 7 个工具，工具绑定当前账号，有步数上限和收尾总结，失败如实汇报，工具参数错误会回报给模型。

**不足**

1. 没有调研类工具：只能 `find_topics` 一把抓热点，不能搜博主、看作品、看详情。
2. 调研结果没有地方存：聊完就埋在对话历史里，写稿用不上。
3. 工具结果直接截前 1500 字符（可能截断 JSON），历史里旧工具结果原样占上下文。
4. 一步里多个工具调用是串行执行的；MAX_STEPS=8 对多步调研偏少。
5. 平台能力没有统一声明：哪个平台支持什么，模型不知道。

## 3. 改造方案

### 3.1 平台能力层（sources）

每个平台实现同一组可选能力，并声明支持情况：

| 能力 | 说明 | 返回（精简后） |
| --- | --- | --- |
| `search_posts(keyword)` | 关键词搜内容（现有） | 标题、作者、互动数、链接、ref |
| `search_creators(name)` | 搜博主 | 昵称、粉丝数、简介、作品数、ref |
| `creator_posts(ref)` | 博主最近作品 | 标题、发布时间、互动数、ref |
| `post_detail(ref)` | 作品详情 | 正文、标签、互动数、热门评论（前 N 条） |

`ref` 是平台内部 ID（如小红书 user_id + xsec_token）的短句柄，由代码维护映射，模型只需原样传回，避免它抄错长 ID。

### 3.2 管家工具（4 个通用调研工具 + 1 个笔记工具）

- `research_search(platform?, keyword)`：搜内容；不指定平台则并行搜所有已启用平台
- `research_creators(platform, name)`：搜博主
- `research_creator_posts(platform, creator_ref, limit=10)`：看博主作品，按互动排序可选
- `research_post(platform, post_ref)`：看单篇详情和热评
- `save_note(title, content)`：把调研结论（对标账号画像、爆款规律）存进账号档案，写稿时作为上下文注入

返回统一为精简 JSON，超出预算时截断并附「还有 N 条，可加 limit/换关键词」的提示；不支持的能力返回明确原因。

### 3.3 循环与上下文

- 同一步里多个工具调用 `asyncio.gather` 并行执行。
- MAX_STEPS 8 → 12；prompt 写调用预算：简单问题 1–3 次，对标分析 5–10 次，先宽后窄。
- 工具结果先按字段精简再入上下文；历史中较早的调研工具结果只保留一行摘要（tool result clearing）。
- 账号「调研笔记」进入写稿流水线的上下文，与长期规则一起生效。

### 3.4 暂不做

- 多 agent / 子 agent：token 成本约 15 倍，当前任务规模单 agent 足够；等需要「一次分析 5 个对标账号」时再引入并行子任务。
- 自动发布：风控风险，保持手动。

## 4. 风险

- 按人抓取比关键词搜索更容易触发风控：每平台限速 + 短期缓存，失败如实返回。
- 各平台接口会变：每个能力都有离线 mock 测试 + 手动实测脚本。
